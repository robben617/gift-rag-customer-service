# 联合路由提示压缩

联合路由已经把意图分类和检索改写放到一次工具调用中。上一轮固定集通过了 18/18 轮，但全链路 Token 从 57,637 增至 58,634。这一步将重复的分类说明集中到系统提示，工具定义保留字段类型、意图枚举、置信度范围和检索词长度约束。提示只保留一个改写示例。

提示依然要求从问题中提取现有实体，改写时保留型号、数值、时间、否定、条件及每个子问题。订单实体完整匹配、置信度门槛、指代补全、原问题召回及生成后的质量检查沿用原有实现。调用参数、响应字段和异常回退保持一致。

初次压缩的 18 轮问答均通过，两个“到货再给钱”近义问法被标为商品咨询。它们仍走同一知识库路由，也命中了正确证据。最终提示为订单意图补充到货后付款的分类规则，重新测量用量和问答质量。

## 对比口径

[压缩前基线](rag-joint-routing.md)对应提交 `ccffae4`。复测沿用 60 条 FAQ、同一模型与三套已冻结的对话数据，报告保存数据和源文件指纹。联合路由用量从 `routing.classify_and_rewrite` 阶段的实际请求中汇总，另外列出全链路用量。这样可以区分提示输入的直接节省，以及模型输出、检索路径和纠正回合变化带来的用量波动。

```powershell
python scripts/run_live_rag_benchmark.py --run-dir reports/rag-live/compact-routing-final --timeout 240
python scripts/run_live_rag_benchmark.py --dataset data/rag_guard_eval.json --run-dir reports/rag-live/compact-routing-controls-final --timeout 240
python scripts/run_live_rag_benchmark.py --dataset data/rag_routing_eval.json --run-dir reports/rag-live/compact-routing-review --timeout 240
```

三组都是隔离服务上的固定题实测。各次运行的模型服务响应和冷启动耗时会波动。自动化回归覆盖已知订单实体、异常返回、改写回退与工作流，真实 HTTP 评测使用 FAQ 索引，订单后端禁用。

本页的 18 轮短提示结果也作为后续发布检查的固定集 Token 基线。[对话发布检查](rag-release-gate.md)

两个版本的 18 轮均有完整追踪和 Token 用量，数据、模型、运行参数一致。指纹比对确认评测涉及的源文件中只有分类器发生变化。联合路由平均每次少 384 个输入 Token，各阶段调用次数一致。两道货到付款题在最终版均归为订单咨询，固定集的意图标签和路由目标与压缩前逐轮一致。本轮确认的收益是用量，去掉首轮后 P95 反而略高，单次小样本不足以判断尾延迟改善。

路由与工作流的 79 项自动化回归全部通过。补充样本 5/5 通过，意图标签和路由目标逐轮一致，全链路 Token 从 16,141 降到 13,937。

无证据对照 6/6 通过，3 条风险题均转人工。调用仍为 35 次，全链路 Token 从 16,463 降到 13,883。三组共 29 轮的意图标签和路由目标都与压缩前逐轮一致。

另用真实模型直测 6 条路由用例，均在一次模型调用中返回预期结果。两个合成单号分别正确提取为订单号和快递号并选中 SQL 分支，探针未执行数据库查询。其余用例验证了货到付款分类、商品型号与续航条件、门店地区与日期、发票收件方式和时间两项诉求。
