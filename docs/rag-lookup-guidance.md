# 在资料有依据时提供查询入口

首次发布检查里，预售问题同时问了实际出库时间和去哪里核对。检索已经命中 FAQ-011。覆盖核验知道资料只说“预售商品以页面标注时间为准”，但仍要求提供该订单的具体出库时间，并将页面指引判为不充分。第一轮因此转人工，第二轮改问普通现货时被同一待审批任务阻塞。

修复把两种信息分开处理。用户明确问去哪里或如何核对，且资料为同一事项指定了查阅入口时，答复可以给出这个入口，并说明资料暂无法确认个案值。以预售为例，去商品页查看标注的发货时间是有依据的建议，某件商品实际在哪天发货需要商品页或订单数据。

## 规则如何生效

- 生成前的证据核验、生成提示、生成后的回答核验根据同一条已补全的用户问题判断是否提示查阅规则。检测只看是否问了“看哪里”“去哪儿查”“如何查询”等入口或方法，具体入口及其适用范围仍要核对资料。
- 候选答复须给出资料中指向同一事项的查阅入口。用户同时问个案值而资料缺失时，还须明确区分未知值。核验结果沿用原文引用、回答片段校验和忠实度门槛。
- 用户只问个案事实、指引来源泛泛、还有其他独立问题无证据，或要求退款执行、价格承诺、健康安全保证时，仍按原覆盖标准和业务护栏处理。资料不足或服务不可用时按原流程转人工。

这一规则只改变适用问法中的核验与生成提示，额外提示仅在有查阅请求时加入。修复后的预售题通过自助回答，不再创建该轮待审任务，下一轮可正常进入流程。已有待审批任务的会话行为与权限保持原有规则。

初版恢复了两轮对话，但人工核对发现首轮把“我的订单”也称为最准确的查看位置。订单状态入口与预售日期的来源是不同事项。最终提示要求只用直接支持所问入口的资料，并在答复混入别的入口且将其视为同一事项的来源时判为不通过。

## 复现

```powershell
python scripts/run_live_rag_benchmark.py --dataset data/rag_lookup_guidance_eval.json --run-dir reports/rag-live/lookup-guidance-final --timeout 240
python scripts/rag_release_gate.py --run-dir reports/rag-release/lookup-guidance-final
```

补充集在运行前冻结，共 5 段、6 轮。正例是预售查询入口及切换到普通现货的追问；反例覆盖只问确切日期、查阅入口无证据、剩余独立问题无证据，以及过敏安全保证。原发布集数据、阈值与 Token 预算保持原样。

核验的语义判断由模型完成，代码校验引用片段是否存在。现有对照是固定 FAQ 的实测，未接入真实商品页面或订单库。

## 验证结果

补充集 6/6 通过。预售问题回答查阅入口，并说明无法确认具体日期；现货追问回答付款后 1–3 个工作日发货。两轮均通过前后核验，未生成审批任务。4 个证据不足反例均转人工，其中 1 个涉及过敏安全保证。生成、工作流、评测和 API 的 226 项自动化回归全部通过。

原发布集的 `dialogue-401` 也恢复两轮自助。第一轮给出商品页预售说明，并说明当前资料无法确认实际出库日期。第二轮按普通现货答复付款后 1–3 个工作日发货。人工核对确认首轮没有再混入订单状态入口。

最终提示的首次固定集实测为 17/18，用量 54,468，低于 57,018 的预算。唯一失分 `dialogue-103` 是货到付款题：找到 FAQ-060 后，生成仍暗示个别型号需要另行核实，忠实度检查最终拦下了草稿。该问法没有触发查询指引，普通问题的提示模板与修改前相同。该次结果保留供复核。

同次发布检查中，原发布集从 15/17 提升到 17/17，证据组 10/10，4 条风险题与 4 条证据不足题均按标注转人工。待审批阻塞从 1 轮降为 0。整体门禁当次因固定集失分返回 `1`，不是数据或用量缺失。

随后用同一源码、固定题、语料和模型独立复跑固定集，恢复到 18/18，用量 52,572。使用该次固定集报告和字节未改动的同版发布集报告执行 `--check-only`，门禁返回 `0`。两次固定集结果分开保留，表明货到付款问题仍可能因模型生成不同表述而误转人工。预售及条件切换在原题和补充题上均通过。
