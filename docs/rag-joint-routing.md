# 合并意图分类和检索改写

上一版在同一轮 RAG 对话中先请求模型分类，再发一次请求改写检索词。固定 18 轮评测里，分类节点累计 40 次模型调用，其中还包含部分多轮指代消解。本次让分类工具同时返回可选的 `rewritten_query`，由路由器直接使用，不再发送独立改写请求。

`resolved_query` 保留补全后的用户原意，仍用于资料覆盖核验、回答生成和回答覆盖核验。改写值只作为双路检索的一路输入，原问题召回、检索不足后的改写和扩展仍按原路径执行。

## 结构化结果与回退

| 情况 | 处理 |
|---|---|
| 意图有效、检索改写有效 | 只有包含 RAG 检索的路由才使用模型返回的改写 |
| 改写缺失、空白、多行、超过 100 字或类型错误 | 保留有效意图，使用补全后的原问题作为检索词 |
| 分类输出无法解析、意图未知或置信度不在 0 到 1 | 沿用本地关键词分类与原问题 |
| 模型输出订单号、快递号或商品名 | 核对实体可从传给分类器的问题中找到。单号要求完整匹配，避免让模型补出的号码触发订单查询 |
| 售后规则、低置信度订单路由、闲聊与商家信息 | 仍由代码执行各自的路由规则，订单归属由订单服务校验 |

订单号匹配只校验字面来源，实体的业务含义仍由模型判断。改写的长度与格式可代码验证，是否完整保留用户限制仍需检索和回答回归覆盖。

初次运行发现，指定快递问题虽然召回了明确说明“不支持指定快递”的 FAQ，草稿依然建议向人工确认能否指定。质量门拦下了该草稿。本轮补充生成规则，资料明确支持或不支持时直接回答，仅在资料记录了例外或替代办法时提供这些信息。

新样本是按冻结 FAQ 在运行前逐条编写和标注的 4 段、5 轮对话，覆盖发货后地址修改及追问、省内外配送时效、纯问候、无证据的节日自提时间。三个数据集均经真实 HTTP 服务运行，使用项目配置的对话 API 与本地 BGE，禁用外部搜索和订单后端。订单号真实性、路由置信度和订单归属由受控回归分别验证。

对比基线位于提交 `60602f5` 的[检索优化报告](baselines/2026-11-19-rag-performance-optimized.json)。基线模型调用记在 `graph.classify_intent`，本次报告把联合调用标记为 `routing.classify_and_rewrite`。对比整个分类节点时，两类调用相加，以便纳入同一节点内的指代补全。

## 固定集最终对比

2026-11-19 使用同一套 18 轮固定题、60 条 FAQ 和模型配置复测。两版均关联到 18 份请求追踪，模型尝试次数等于逻辑调用次数，无重试或 Token 缺失。最终版包含联合路由和上面的生成约束两项改动。

| 指标 | 上一版 | 最终版 |
|---|---:|---:|
| 对话轮次通过 | 18/18 | 18/18 |
| 整段对话通过 | 12/12 | 12/12 |
| 安全轮误转 | 0/14 | 0/14 |
| 无证据轮次通过 | 4/4 | 4/4 |
| 证据组通过 | 13/13 | 13/13 |
| 分类节点模型调用，含多轮指代补全 | 40 | 23（−42.5%） |

最终版运行了 17 次联合调用和 6 次指代补全，省掉原先 17 次独立的路由改写。检索改写、扩展和资料覆盖核验的调用数在本次对比中分别为 8、8 和 21，两版相同。输入 Token 增加 1,122，输出 Token 减少 125。后续对重复的提示内容做了压缩，见 [用量与质量对比](rag-routing-prompt.md)。

固定集包含用于开发的样本，时延会随本机运行和供应商响应波动。新增样本提供了额外覆盖，生产表现仍需要真实流量验证。[最终逐轮报告](baselines/2026-11-19-rag-joint-routing-final.json)
