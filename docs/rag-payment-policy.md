# 全平台支付规则的原文答复

此前的货到付款试题命中了 FAQ-060。模型在复述“所有订单需在线支付”后仍建议为个别型号另行核实。忠实度核验拦住了草稿，但用户因此被转人工。单独复跑时又答对了同一题，说明规则明确时仍会受生成表述波动影响。

货到付款现可走原文答复。系统先按原有流程完成意图路由、人工介入预判及带权限过滤的召回，再核对以下条件。

- 用户原问与补全后的问法都完整匹配单一支付方式咨询。句中追加订单状态、交易操作、运费到付或其他问题时，仍走常规核验。模型改写删掉限制也无法让原问触发直接引用。
- 在核验窗口内找到一份 `faq_json`，其问题和完整回答与核准 FAQ 匹配。检索到另一个提及该支付方式的资料，或原 FAQ 残缺、改版时，回到普通 RAG 路径。引用使用实际检索分块的 ID 和序号，普通入库不需要使用评测集的 `faq-060` 编号。
- 命中时回复逐字来自资料，附对应的引用编号。证据记录保留原文与答复哈希，`generation.policy_quote` 记录实际走过的分支。忠实度的 `1.0` 来自原文一致性校验。最终结果仍经过现有质量节点和 JSON/SSE 的发布检查。

目前仅启用了核准的货到付款规则。规则由代码和 FAQ 原文共同限定，更新条件或新增例外时应审核完整原文后再扩展。冲突检查限于当前核验使用的前五条资料，完整语料的一致性仍需在入库和政策变更时检查。

发布门禁同时验证候选报告中每个源码指纹，使后来加入部署清单的支付模块发生变化时，之前的报告也会失效。

```powershell
python scripts/rag_release_gate.py --run-dir reports/rag-release/payment-policy
```

补充集 6/6 通过。3 种支付问法均逐字引用 FAQ，检索和回包核验不调用生成模型，每轮仅保留一次意图分类与改写调用。3 个边界问法均未走原文答复，并按预期转人工，覆盖运费到付、实际扣款状态和过敏保证。

固定集 18/18 通过。两轮货到付款都进入原文答复分支。与上次通过门禁复核的固定集报告相比，单轮“东西到了手上再给钱”的调用从 5 次降为 1 次；从手机壳话题切换到货到付款的调用从 9 次降为 2 次，额外的一次用于多轮指代补全。整组从 102 次、52,572 Token 降至 91 次、46,735 Token，仍低于 57,018 的预算。整组用量也受其他问题的模型输出波动影响。

生成、工作流、评测和 API 的 243 项自动化回归通过。用例覆盖改版及冲突资料、截断文本、问句被改写后丢失限制，以及低相似度召回后的原文引用。

原发布集 17/17 通过，4 条风险题和 4 条证据不足题均按预期转人工，没有待审阻塞。整体门禁返回 `0`。实测后核对了源码、数据及语料指纹，也逐条检查了原文答复的引用编号与实际分块是否相符。
