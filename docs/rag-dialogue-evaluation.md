## 复现

```powershell
python scripts/run_live_rag_benchmark.py --validate-only
python scripts/run_live_rag_benchmark.py
```

需要安装项目后端依赖、配置本地 `EMBEDDING_MODEL_PATH` / `RERANKER_MODEL_PATH` 和可用的 `DEEPSEEK_API_KEY`。会产生真实模型调用费用。本轮独立环境使用 Sentence Transformers 3.4.1、Transformers 4.48.3、Hugging Face Hub 0.36.2、Tokenizers 0.21.4；完整实测版本及模型文件哈希在报告中。现有环境若使用新版 Gradio，应另建后端评测环境，避免其 Hub 依赖与旧版 Transformers 冲突；没有改动用户的全局 Python 环境。

运行器新建 `reports/rag-live/<随机ID>/`，复制题目与 FAQ 快照，重新向量化 60 条 FAQ，并使用 FAQ ID 作为 chunk ID。随后启动仅监听 `127.0.0.1` 的临时服务，生成专用普通用户的短期 JWT，通过正常鉴权请求 `/api/chat`，结束后停止自己启动的进程。签名密钥及令牌只在内存/子进程环境中传递，不写入报告。

向量库、会话、监控、检查点、审批任务、日志和文件锁都写入该次独立目录，不使用原有服务或数据。联网搜索关闭，订单后端指向不可用的本机端口；本轮只验证冻结 FAQ 范围，不能称为包含真实订单/外部搜索的生产全链路。使用真实三层记忆和进程内缓存；缓存每次运行重新创建，同次运行可以复用，所以耗时不属于冷启动基准。

产物包括 `dataset.json`、`corpus.json`、`manifest.json`、`report.json`、私有 `server.log` 和隔离运行数据。启动失败也写 `complete=false` 报告，不能算通过。退出码 0 表示所有轮次断言通过，其余评测失败为 1。目录必须是全新的，避免误用旧索引。

如果使用已有的 HTTP 评测入口，也可指定此数据集：

```powershell
python scripts/run_dialogue_benchmark.py --dataset data/rag_dialogue_eval.json --base-url http://127.0.0.1:8000 --deployment-id <服务标识>
```

这种方式需另行提供 `DIALOGUE_EVAL_TOKEN`，且目标服务的索引必须使用相同 FAQ ID；普通文档分块产生的随机 chunk ID 不能直接与本集证据标注比较。

## 新的评分约束

- `evidence_groups`：每组是同一证据点的可替代 FAQ ID，所有组都必须至少命中一个；证据组通过率的分母是有证据标注的轮次数，不是全部轮次，也不是原检索基线的 Recall@5。
- `answer_groups`：每组至少包含一种必要事实表达，所有组必须满足。进行大小写、空白、部分区间连接符归一化，但不替代人工语义评审。
- `targets`：检查实际路由，避免通用问候或错误政策回答被算作通过。
- 若下一轮返回上一轮相同的 `review_task_id`，该轮属于审批阻塞：记录 `prior_review_pending`，不得把它算成新问题的正确无答案处理。后续轮次不再发送，仍计入总分母；报告 `review_blocked_turns` 和 `complete=false`。

误转人工率仍只在有效处理的安全轮上计算，必须同时看观测覆盖率。被审批阻塞的轮不进入这个指标的有效分母，但不能算轮次通过。风险轮执行错误或审批阻塞按风险漏拦保守计入。上一轮售后集的指标与复现见 [对话评测说明](dialogue-evaluation.md)。

## 本轮修复与剩余问题

1. 原先先把追问改写成“邮件 配送时间”，再做指代消解，容易引入物流语义；而消解结果只送检索，没有回传生成节点。现在先对原始追问补全上下文，再分类/改写，并把最终检索查询写回状态供生成、自纠正及响应使用。保留原始问题作为召回兜底，规则型售后澄清仍按原输入提取事实。
2. “先不说退货了，店铺券和平台券可以一起用吗”被售后关键词截走。现在只忽略句首明确结束旧话题的片段；后面的实际退款要求仍触发人工处理。该样本在真实复测中已进入 RAG 正常回答。
3. 门店营业问题被分类为闲聊并返回通用问候。补充商家信息分类提示及闲聊误判保护。该样本在真实复测中检索后进入人工核验，没有编造关门时间。
4. 修复评测器对上一轮审批阻塞的错误计分。

仍存在货到付款、指定快递、发票追问的检索降级，以及明明找到手机壳材质、却因回答包含泛化的不确定表述而转人工的情况。一轮误转还会阻塞同段后续问题。下一步应针对这些失败样本检查原始/改写查询的召回候选、精排顺序、降级判断和逐条事实支持；单独准备未用于调参的题目，校准“可回答/应拒答”的边界，再运行同口径对照。不要仅下调全局阈值来减少转人工。
