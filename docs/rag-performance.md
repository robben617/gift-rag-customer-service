# 对话延迟与模型用量基线

上一轮解决了固定评测集里“有答案却转人工”的问题，但每轮到底串行调用多少次模型、耗时在哪里还不清楚。本轮为共享对话服务加入请求级计时和用量追踪，并修复明确不可重试错误仍重复发送的问题。

## 记录口径

JSON 与 SSE 响应增加 `trace_id`，用于关联 `monitoring.db` 的 `query_records.query_id`。完整记录在新增的 `performance_json` 列中，不通过客服响应返回。旧数据库自动补列，历史记录保持 `{}`，不能追溯为完整用量数据。

| 字段 | 含义 |
|---|---|
| `total_ms` | 从共享服务入口到生成最终响应对象的耗时，含会话锁等待和记忆更新；不含监控落库及 HTTP 传输 |
| `stages` | 会话等待、各图节点、资料/回答覆盖、回答生成、忠实度、改写/扩展、记忆读取/更新的计时；嵌套阶段包含子阶段，不能全部相加 |
| `llm_calls` | 统一客户端的逻辑调用数，包括熔断器直接拒绝的调用 |
| `llm_attempts` | 底层请求尝试数，失败尝试也计入；客户端初始化/响应解析失败也属于尝试失败 |
| `llm_retries` | 同一逻辑调用首次尝试之后的额外尝试数 |
| `usage` | 供应商实际返回的非负整数 Token 字段之和，不用字符数补算 |
| `usage_missing_attempts` | 没有完整返回输入、输出及总 Token 数的尝试数 |
| `usage_complete` | 所有已追踪尝试都提供完整用量；完全没有调用时为真、Token 为 0 |
| `estimated_cost_cny` | 按记录中的项目费率表估算；存在缺失用量或未知模型费率时为 `null` |

成本覆盖**统一 LLM 客户端**，不包含绕过该客户端的外部搜索、OCR、Embedding API 或本地算力。费率是仓库已有配置快照，未作为本轮最新官方报价核验，也未考虑供应商缓存折扣；估算不等于账单。旧 `llm_cost` 数值列为兼容现有界面保留，缺失时仍存 0，但新增日报完整性字段和告警明确提示不能当作完整成本合计。

计时使用单调时钟。请求上下文在图执行线程之间共享一个加锁的累加器，不同请求独立；完成后恢复上下文。监控只增加阶段名、模型名、次数、时间、Token 和异常类型，不记录提示词、生成草稿、API Key 或异常正文。原有监控问题字段仍走 PII 脱敏。

提前返回（上一轮待审批、初始化失败）同样有新追踪记录，不会沿用上一轮账目。业务结果与监控落库解耦，监控写入失败不会把安全答复变成接口错误；评测会把缺失追踪标为不完整。

## 修复无效重试

原实现遇到不可重试错误只是不等待，仍继续循环；默认配置下同一 400/401/403/404 最多请求三次。现在首次失败即停止。429、5xx、超时等可恢复错误保留原重试与退避，熔断器直接拒绝计为一次逻辑调用、零次底层尝试。

受控 HTTP 测试确认上述客户端错误只发一次请求；429、503、超时后成功计为一次逻辑调用、两次尝试、一次重试，首次失败缺失的用量不会被掩盖。该修复不代表正常成功问答减少了模型调用，也不据此宣称线上提速。

异步调用也纳入追踪。底层模型流式请求请求 usage 尾包，兼容只有 usage、没有 choices 的数据包，并在取消时关闭内层生成器。客服 SSE 仍在业务链路完成核验后发送答案；本报告的 HTTP 总耗时不是模型首 Token 时间。

## 减少检索阶段的模型调用

首轮本地召回有候选，但没达到原有相似度门槛时，先用完整用户问题核验前五条候选。资料明确覆盖问题时，直接沿用候选及覆盖结论，省去后续改写和扩展。资料不足或核验不可用时继续原降级流程。最终回答仍须通过忠实度、回答覆盖及高风险承诺规则。

同一次检索内，覆盖核验按问题、候选文档 ID 和模型实际读到的片段计算哈希。前后输入完全相同时复用已得出的充分或不足结论，避免同一批文档被重复核验。候选改变则重新核验，临时错误不进入复用记录。该优化在资料不足且后续候选变化时可能增加一次核验，需要同时比较无证据对照题与普通问答。

## 复现

```powershell
python scripts/run_live_rag_benchmark.py --run-dir reports/rag-live/performance-early-evidence --timeout 240
python scripts/run_live_rag_benchmark.py --dataset data/rag_guard_eval.json --run-dir reports/rag-live/performance-controls --timeout 240
```

运行目录必须尚不存在。评测沿用冻结的 60 条 FAQ、原 12 段/18 轮及 6 条无证据对照题，服务、索引、审批和监控存储均隔离。需要预先可用的本地 BGE 模型和项目模型 API 配置；不会下载模型或模拟真实评测结果。

基线对应本地提交 `f090f6f`，包含追踪和重试修复。在该提交的独立工作树内执行第一条命令，换一个未使用的输出目录，即可按相同配置重跑基线。报告记录数据、模型和源文件指纹用于核对，远端模型输出和实际耗时可能随运行变化。

报告保留质量指标，并按响应追踪 ID 关联每轮内部性能记录，再汇总服务/HTTP P50、P95、调用数、Token、阶段分布。性能完整性与问答质量完整性分开报告，缺失记录不能用 0 毫秒补齐。分位数使用 nearest-rank；小样本 P95 接近最大值，不能当作生产 SLO。第一轮单列，服务启动已预热本地模型，后续仍可能有供应商及本地缓存影响。

## 实测对比

2026-11-19，使用相同的 60 条 FAQ、12 段/18 轮对话和模型配置，分别启动隔离服务。两次运行均有 18 份完整追踪，实际请求数等于逻辑调用数，重试及用量缺失均为零。

| 指标 | 基线 | 前置资料核验 |
|---|---:|---:|
| 对话轮次通过 | 18/18 | 18/18 |
| 整段对话通过 | 12/12 | 12/12 |
| 安全轮误转人工 | 0/14 | 0/14 |
| 无证据轮次通过 | 4/4 | 4/4 |
| 证据组通过 | 13/13 | 13/13 |
| 模型调用总数 | 142 | 116（−18.3%） |
| 检索改写与扩展调用 | 40 | 16 |
| 资料覆盖核验调用 | 17 | 21 |
| 回答覆盖核验调用 | 13 | 13 |
| 总 Token | 61,025 | 57,637（−5.6%） |
| 按仓库费率估算成本 | ¥0.072525 | ¥0.067241（−7.3%） |
| 检索节点 P50 | 8.37 秒 | 3.09 秒 |
| HTTP P50 | 10.05 秒 | 8.92 秒（−11.3%） |
| HTTP P95 | 29.49 秒 | 27.60 秒 |
| 除首轮外的 HTTP P95 | 24.09 秒 | 12.25 秒 |

原集的 4 条无证据题合计从 29 次增加到 33 次模型调用。前置核验需要先检查初始候选，后续检索找到不同资料时还要核验一次。正常有证据的问题省掉的改写与扩展覆盖了这部分增加。以上结果来自固定开发集的两次实测，生产延迟和成本还取决于问题分布、本地推理和供应商响应。18 轮的 P95 恰好等于最大值。

优化后另跑了 6 条无证据对照，全部通过，3 条风险请求均转人工。对照集共 41 次调用、15,981 Token，追踪完整，未触发回答生成。

## 验证范围

自动化回归覆盖线程上下文传递与请求隔离、失败与重试计数、缺失或异常类型的 usage、异步与流式尾包/取消、旧库迁移、监控缺失标记，以及 JSON/SSE 业务等价和人工审批链路。模型客户端测试使用受控 HTTP 替身，实际耗时与能力另由真实服务评测验证。

全组回归共 482 项通过，9 项按项目默认配置排除。Ruff 检查通过。

优化后，分类节点仍有 40 次模型调用，累计约 34.36 秒。下一步优先验证能否在一次结构化请求中返回意图与检索改写，保留实体、置信度和上下文校验，再用固定集和新增人工复核样本对比。
