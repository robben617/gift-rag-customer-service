## 1. 一页速览

### 1.1 一句话

一套面向**私域礼赠场景**的电商智能客服系统。它不追求「平均准确率再高一点」，而是要解决一个更具体的问题：**让高频重复咨询自助闭环，同时把答错代价高的问答识别出来交给人工**。

### 1.2 三个数字

| 维度 | 现状 | 出处 |
|---|---|---|
| 编排规模 | **13 节点** LangGraph StateGraph（8 条静态边 / 5 组条件边） | `src/graph/workflow.py`，`grep -c add_node` = 13 |
| 知识库 | **60 条 FAQ** → **61 个向量**（collection `ecommerce_knowledge`） | `data/faq/ecommerce_kb.json`；`data/chroma/chroma.sqlite3` |
| 质量基线 | Recall@5 **0.7347** / MRR 0.7092 / NDCG@5 0.7048（49 题自建集，仅检索模式） | `reports/benchmark_retrieval_20261013_230049.json` |
| 工程质量 | **410 条测试通过**（另 9 条按 `slow`/`integration` marker 默认排除） | 2026-11-04 实测 |

### 1.3 三条回答路径（理解系统的关键）

用户问一句话，系统可能走三条完全不同的路径。**看不清这三条，就会误判系统行为**（例如「为什么这个问题没有检索条数」）。

| 路径 | 触发条件 | 是否经过 LLM | 是否有检索证据 | 典型问题 |
|---|---|---|---|---|
| **工具直答** | 命中订单号/快递单号 → `sql` 节点；命中退货子场景（窗口/运费/时效/质量争议）→ `policy` 节点 | 否（结构化直出） | 否 | 「我的订单到哪了」「退货包运费吗」 |
| **RAG 检索生成** | 其余业务问题 → `retrieve` → `generate` | 是 | 是，带来源 | 「保质期多久」「礼盒里有什么」 |
| **转人工** | 情绪 extreme / 愤怒+高敏意图 / 退款投诉法律关键词 / 忠实度不达标且高敏 | 部分 | 视路径 | 「我要退款」「再不处理我就起诉」 |

> 这条区分来自 `src/graph/workflow.py` 的 `route_decision()`：退货类问题**优先**走 `policy` 结构化政策，未命中才回落到 RAG。因此退货问题「检索到 0 条」是正常现象，不是故障。

### 1.4 五分钟启动（零依赖演示）

```bash
git clone https://github.com/robben617/gift-rag-customer-service.git
cd gift-rag-customer-service
python scripts/demo_offline.py
```

不下载模型、不填 Key、不起 Docker。装了 Gradio 会自动开 `http://127.0.0.1:7863`，否则进终端问答。

> ⚠️ 这条链路**只做离线 FAQ 关键词检索 + 原文直出**（60 条 FAQ，字符二元组 IDF 加权，纯标准库），**不经过 LLM 生成、claims 核验与护栏**。它的输出**不代表系统真实回答质量**，只用于「先看见界面长什么样」。完整链路见第 10 章。

## 2. 业务背景与产品定义

### 2.1 业务链路（一个二维码怎么变成一次咨询）

| 环节 | 谁在动 | 发生了什么 |
|---|---|---|
| ① 选品采买 | 客户企业（运营/采购） | 按节假日档期采买礼赠品，以食品类为主 |
| ② 发放 | 客户企业 | 发给自有客户 / 员工，实物礼品随箱附卡片 |
| ③ **扫码** | 收礼用户 | 礼品外包装/卡片上的二维码是**唯一私域入口** |
| ④ 落地页 | 私域页面（H5/小程序） | 展示礼品详情、保质期、物流进度、售后政策 |
| ⑤ 咨询 | 收礼用户 → 客服 | 页面内嵌客服入口，**本系统在此介入** |

### 2.2 三个业务约束（所有技术选型的出发点）

**约束一：流量是脉冲，不是缓坡**

二维码在发货那一刻集中触达，用户几乎在同一周内涌入。行业公开经验值：节假日/大促峰值咨询量为日常的 **3–8 倍**（客服外包行业普遍按 3–5 倍配坐席，爆款品类可达 8–10 倍）。

> 📌 该区间为**行业经验值**，非本项目客户实测。客户侧真实日均/峰值量需由运营提供；做容量设计时按 3–8 倍预留。

**约束二：用户是被动收礼人，不是主动购物人**

他不熟悉品牌、没看过商品页、没有购物车与订单记录。因此：

- 问法极其口语化（「这玩意儿过期没」）
- 常常**无主语、不带订单号**（「能退吗」）
- 没有订单上下文，必须靠会话记忆与追问补齐

**约束三：答错代价严重不对称**

| 回答类型 | 答对收益 | 答错代价 |
|---|---|---|
| 商品规格 | 省一次人工 | 低，用户再问一次 |
| **食品保质期 / 过敏原 / 能否食用** | 省一次人工 | **食品安全事故、人身伤害** |
| **退款时效 / 赔偿标准** | 省一次人工 | **客诉、赔付、资损** |
| **价格与赠品承诺** | 省一次人工 | **「你们承诺过」，无法自证** |

> 结论：**不能用「整体准确率」衡量这个系统。** 「平均 95% 正确」在这里没有意义，因为剩下 5% 恰好落在最不能错的那几类上。这是「幻觉检测 + 高敏护栏 + 转人工」这一整条链路存在的唯一理由。

### 2.3 交付形态

**乙方交付**。开发方是软件交付团队，最终使用方是客户的私域礼赠业务团队。

对外表述统一为「**为客户交付的**私域礼赠智能客服系统」，不要写成「公司自己的业务」。

### 2.4 产品目标（按优先级，不可颠倒）

1. **高频咨询自助闭环** —— 能不转人工就解决
2. **转人工时体验不降级** —— 上下文无缝交接，用户不重述
3. **高风险回答不乱承诺** —— 先守红线，再谈效率

### 2.5 红线（不可突破）

- 食品安全、退款时效、价格承诺类问题 → **必须人工把关，或明确拒答**
- 任何回答**不得出现知识库无依据的具体数字**（几天、多少钱、百分之几）
- 检索不到时**必须说不知道**，不允许「根据常识推断」

### 2.6 明确不做的事（范围外）

| 不做 | 原因 |
|---|---|
| 自动执行退款 / 改单 / 发券 | 资金与订单写操作必须人工，系统只读 |
| 替代人工客服团队 | 定位是「分流 + 兜底」，不是替代 |
| 商品推荐 / 营销触达 | 不属于客服场景 |
| 多租户 SaaS 化 | 当前为单客户交付，未做租户隔离 |
| 语音客服 / 电话外呼 | 当前仅文本（含 SSE 流式） |

## 3. 用户角色与权限模型

### 3.1 四个角色

| 账号 | 密码 | 角色 | 内容等级 | 能看什么 |
|---|---|---|---|---|
| `admin` | `admin123` | 管理员 | `vip` | 全部内容 + 管理面（上传/统计/评估） |
| `vip` | `vip123` | VIP | `vip` | 全部内容，无管理权限 |
| `member` | `member123` | 会员 | `member` | public + member |
| `normal` | `normal123` | 普通 | `public` | 仅 public |

> 默认由 `ENABLE_DEMO_USERS=true` 开启（`.env.example`）。**生产必须置为 false**，否则明文弱口令直接暴露。

### 3.2 内容级权限隔离（本项目最容易被低估的设计）

权限模型不是「回答时过滤」，而是**检索时过滤**——不该看的内容根本不进入模型上下文。

```
public(0) < member(1) < vip(2)
可见性：用户等级(rank) >= 文档等级(rank)
Chroma filter: access_level <= {用户 rank}
```

三个关键实现细节：

1. **用整数 rank，不用字符串比较**。字典序下 `"member" < "public" < "vip"` 是错的，语义会错位。
2. **fail-safe 默认 public**。任何调用点漏传 `access_level`，默认取最低权限——宁可少给，绝不泄漏。
3. **缓存 key 必须含 access_level**。否则 VIP 命中过的缓存会被 public 用户读到，这是 RAG 系统最常见的数据泄漏路径。

单一定义源：`src/access.py`。全链路 **7 个调用点**逐层透传（六级降级 / 查询扩展 / 双路召回 / 自纠正 / 工作流兜底等）。

### 4.2 用户旅程（主流程）

```
扫码进私域页
   ↓
点客服入口，问「这玩意儿过期没」
   ↓
[意图分类] product_consult
   ↓
[是否需要人工] 情绪 calm、无敏感词 → 否
   ↓
[检索] L1 双路召回 → 命中 FAQ「保质期」
   ↓
[生成] 基于证据作答，附来源
   ↓
[质量评估] claims 核验通过（faithfulness 达标）
   ↓
回复用户（1–2 秒）
```

异常分支：

```
用户：「我要退款，再不退我就起诉」
   ↓
[情绪] extreme（法律/威胁词）
   ↓
[check_human] 直接判定 needs_human，priority=high
   ↓
[human] 生成交接包（query + intent + emotion + entities + memory + attempted_actions + reason）
   ↓
客服在 7862 管理台看到工单，直接接手；用户在 7861 同窗口继续对话
```

### 5.3 LangGraph 13 节点明细

| # | 节点 | 函数 | 职责 | 出口 |
|---|---|---|---|---|
| 1 | `classify_intent` | `classify_intent` | LLM Function Calling：6 类意图 + 实体抽取 | → check_human |
| 2 | `check_human` | `check_human_needed` | 情绪/敏感词/置信度初筛是否需人工 | 条件边 `route_decision` |
| 3 | `retrieve` | `retrieve_docs` | L0–L3 级联向量检索（含双路、分解、扩展） | 条件边 `check_retrieval` |
| 4 | `web_search` | `web_search` | L4 联网兜底（智谱优先，Tavily 备选） | → generate |
| 5 | `generate` | `generate_answer` | 基于证据生成回答 | → evaluate_quality |
| 6 | `evaluate_quality` | `evaluate_quality` | claims 级核验 + 高敏判定（0.7 / 0.85） | 条件边 `evaluate_decision` |
| 7 | `human_approval` | `human_approval` | **真正的 HITL 中断点**（`interrupt_before`） | 条件边 `human_decision_edge` |
| 8 | `rewrite_and_retrieve` | `rewrite_and_retrieve` | 自纠正：改写 → 重检索（≤3 轮） | 条件边 `retry_after_rewrite` |
| 9 | `human` | `handle_human` | 生成交接包，转人工 | → END |
| 10 | `sql` | `handle_sql` | 订单/物流工具直答 | → END |
| 11 | `policy` | `handle_policy` | 退货结构化政策直答 | → END |
| 12 | `direct` | `handle_direct` | 闲聊/无关问题直答 | → END |
| 13 | `error` | `handle_error` | 异常兜底 | → END |

**条件边（5 组）**

| 判定函数 | 分支 |
|---|---|
| `route_decision` | rag / sql / human / policy / direct |
| `check_retrieval` | generate（有结果）/ web（空或降级≥L4） |
| `evaluate_decision` | end（通过）/ human_approval（不通过且未超轮次） |
| `human_decision_edge` | end（approve）/ rewrite（reject） |
| `retry_after_rewrite` | retrieve / error（达上限） |

**关键常量**：`MAX_LOOP_COUNT = 3`（`workflow.py:42`）、`MAX_LLM_CALLS = 8`（`self_correction.py:27`）。

> ⚠️ 这是一个**有界自主**系统：3 轮改写上限 + 8 次 LLM 调用预算 + 明确终止节点，不存在无上限循环。

### 5.4 检索降级 L0–L5

| 级别 | 策略 | 何时触发 |
|---|---|---|
| L0 | 复杂查询分解（「和/对比/区别」→ 子问题并行） | 检测到复合问法 |
| L1 | 双路召回稠密检索 + 合并去重 + Reranker | 默认路径 |
| L2 | LLM 改写查询 → 重检索（≤2 次） | L1 无结果或分数低 |
| L3 | Multi-Query + HyDE → 并行检索 | L2 仍不足 |
| L4 | 联网搜索（智谱 / Tavily） | 检索为空或降级≥4 |
| L5 | 诚实兜底（「根据已有信息无法确认，建议咨询人工客服」） | 全部失败 |

> 设计原则：**宁可说不知道，不许猜**。L5 是产品红线，不是技术失败。

完整 10 篇见 `docs/ADR.md`。

## 6. 核心机制详解

### 6.1 「三个 faithfulness」不能混用（最容易出错的地方）

代码里有三套不同实现、不同量纲的数，**互相不可比较**：

| 名称 | 数值 | 实现 | 含义 |
|---|---|---|---|
| 评测脚本的 `faithfulness` | **0.657** | `metrics.py::calculate_faithfulness_fast` | 「标准答案 ↔ 检索文档」的 bge 余弦相似度，**仅检索模式的代理值** |
| 生成忠实度（G-Eval） | **暂无数字** | 需 `--with-generation --use-llm-eval` | LLM 对**实际生成的回答**逐条核验；**尚未留完整跑分** |
| 运行时护栏阈值 | 0.8 / 0.85 | `hallucination_detector.py` claims 聚合 | `(supported + 0.5×partial) / 总claims`，作用于生成阶段 |

> 对外只能说：「检索侧代理值 0.657；生成侧忠实度还没跑完整 LLM 裁判，不给数字。」把 0.657 说成「生成忠实度 66%」是错的。

### 6.2 claims 级幻觉检测为什么重要

常见做法是让 LLM 自评一个 0–1 的「忠实度总分」。问题有两个：

1. **模型自偏**：倾向于给自己的输出打高分。
2. **均值掩盖**：10 句话里编了 1 句，总分可能还是 0.9，问题被平滑掉。

本项目改为：拆成 claims → 逐条判定 supported / partial / unsupported → 聚合。好处是**能定位到具体哪一句在编**，自纠正时也能针对性补信息。

### 6.3 高敏护栏的触发逻辑（注意：不是「一律」）

```
if 命中高敏（价格/退款/政策承诺） and faithfulness < 0.85:
    → 转人工核验
else:
    → 正常输出
```

同时，**退款请求**走另一条更硬的规则：`human_in_loop.py` 的 `refund_request` 场景直接判 `needs_human`（关键词：退款/退钱/退款到账/退款失败），不依赖忠实度。

> 口径提醒：对外不要说「资金类一律人工把关」，准确表述是「退款类请求直接转人工；价格与政策承诺在忠实度低于 0.85 时转人工核验」。

### 6.4 转人工的判定来源（5 条）

| 来源 | 规则 | 优先级 |
|---|---|---|
| 情绪 extreme | 辱骂/威胁/法律升级 | high |
| 情绪 angry + 高敏意图 | return_refund / complaint / order_query | high |
| 场景关键词 | `refund_request` / `complaint` / `sensitive_topic` / `high_value_order` | high / high / high / medium |
| 回答质量 | 命中「不确定」类话术模式 | low |
| 意图置信度 | `confidence < 0.4`（仅当调用方显式传入） | low |

**交接包内容**：`query + intent + emotion + entities + memory + attempted_actions + reason`。这是「用户不重述」的技术保证。

### 6.5 三层记忆

| 层 | 机制 | 解决什么 |
|---|---|---|
| 短期窗口 | 最近 6 轮原文 | 保证最近上下文精确 |
| 滚动摘要 | 窗口外对话 LLM 压缩（实体感知，600 token 预算） | 长对话不爆上下文 |
| 实体台账 | 正则抽取券/订单/金额，逐轮更新 | 「上次那个券」能解析到具体值 |

配套**指代消解护栏**：即使意图被分类为 `chitchat`，只要句子里含指代词（「那个」「它」「上次」），也强制走 RAG，不允许直接闲聊打发。

### 6.6 政策时效

文档入库时带 `effective_from` / `effective_to`。检索时过滤掉不在生效窗口内的政策，并在写入后主动失效相关缓存。

> 这解决的是「文件更新后旧版本仍在流通」——在礼赠场景里，同一句「退货时限」在不同档期答案可能不同。

### 6.7 成本与稳定性

| 机制 | 数值 | 作用 |
|---|---|---|
| LLM 调用预算 | 8 次/请求 | 防自纠正叠加导致延迟与成本爆炸 |
| 自纠正轮次 | 3 轮上限 | 有界自主 |
| 熔断器 | 三态 CLOSED→OPEN→HALF_OPEN，LLM/Embedding 独立阈值 | 下游故障快速失败 |
| 缓存 | Query TTL 3600s / Embedding / LLM 响应 | 降本；Redis 不可达自动降级内存 |
| 重试 | 统一在 `LLMClient`（httpx + 重试 + 降级） | 避免各处重复实现 |

| 2 | 鉴权生效 | 不带 token 请求 `/api/query` | 返回 **401**，不是 200 |
| 3 | 登录可用 | POST `/api/auth/login`（admin/admin123） | 返回 `access_token` |
| 4 | 检索命中 | 带 token POST `/api/query` `{"query":"保质期"}` | `total_found > 0` |
| 5 | 对话可用 | POST `/api/chat` `{"query":"退货包运费吗"}` | 有 `reply`，`target=policy` |
| 6 | 转人工触发 | POST `/api/chat` `{"query":"我要退款"}` | `needs_human=true`，`human_priority=high` |
| 7 | 权限隔离 | 同上问题用 normal 与 vip 账号对比 | 两者检索结果集不同 |
| 8 | UI 可渲染 | 浏览器打开 7861 | 出现聊天框与发送按钮，控制台无报错 |

### 10.6 已知坑位（照这个顺序排查，能省 80% 时间）

| 现象 | 根因 | 处理 |
|---|---|---|
| 7861 打开是空白/组件错乱 | 同进程 launch 多个 Gradio Blocks | 一个 UI 一个进程 |
| 聊天页恒显示「系统暂时繁忙」 | `API_BASE_URL` 没设，连了 `rag-api:8000` | `.env` 设 `http://127.0.0.1:8000` |
| `/docs` 页面空白 | Swagger 静态资源走 CDN，被无代理环境挡住 | 需能访问 CDN 的网络/代理 |
| 端口被占 | 上一次进程未退 | `netstat -ano \| findstr :8000` → `taskkill /PID xxx /F` |
| 控制台中文乱码 | Windows 终端编码 | 设 `PYTHONIOENCODING=utf-8` |
| 检索结果为空 | 知识库空 / 阈值过高 / 权限不足 | 先 `ingest_faq.py`；再降 `RETRIEVAL_SIMILARITY_THRESHOLD`；最后确认账号等级 |
| Redis 连不上 | 未启动 | 正常，自动降级内存缓存 |
| 图片解析报 `Model does not exist` | SiliconFlow 模型名与账号权限不符 | `python scripts/debug_sf_models.py` 查可用模型 |
| 想清空知识库重建 | — | 删 `data/chroma` 目录 → 重启 API → 重新入库 |

### 11.4 Recall@5 的口径（必须说清楚）

判定方式：Top-5 中**存在**与标准答案 embedding 余弦相似度 ≥0.70 的文档，即算命中。

- 这是**命中率（hit rate）**口径，不是标准 IR 中需要逐文档相关性标注的 recall
- 评测集为**自建 49 条**，定位是**回归验证**，不是对外精度承诺

## 15. 附录

### 15.1 术语表

| 术语 | 含义 |
|---|---|
| **Agentic RAG** | 检索不是一次性的，而是带评估、自纠正、多级降级的闭环 |
| **L0–L5** | 六级检索降级：分解 → 双路 → 改写 → 扩展 → 联网 → 兜底 |
| **claims 级核验** | 把回答拆成若干断言，逐条判断有无证据支持，再聚合 |
| **HITL** | Human-in-the-Loop，人工介入；本项目用 `interrupt_before` 真中断 |
| **交接包 handoff_payload** | 转人工时打包给客服的上下文（query/intent/emotion/entities/memory/attempted_actions/reason） |
| **access_level** | 内容等级 public(0) < member(1) < vip(2) |
| **chunk_id** | 分块唯一标识，双路召回按它去重 |
| **faithfulness** | 忠实度；**本项目有三个不同口径，见 6.1** |
| **degradation_level** | 本次请求实际走到第几级降级，用于观测 |
