## 1. 一页速览

### 1.1 一句话

一套面向**私域礼赠场景**的电商智能客服系统。它不追求「平均准确率再高一点」，而是要解决一个更具体的问题：**让高频重复咨询自助闭环，同时把答错代价高的问答识别出来交给人工**。

### 1.2 四个数字

| 维度 | 现状 | 出处 |
|---|---|---|
| 编排规模 | **13 节点** LangGraph StateGraph（8 条静态边 / 5 组条件边） | `python -c "...build_rag_workflow().nodes"` → 13 |
| 知识库 | **60 条 FAQ** → **61 个向量**（collection `ecommerce_knowledge`） | `data/faq/ecommerce_kb.json`；`data/chroma/chroma.sqlite3` |
| 检索基线 | 34 道可评分题：Hit@5 **1.000** / Recall@5 **0.990** / MRR@5 **1.000**（Dense + 重排） | `docs/baselines/2026-11-16-rerank.json` |
| 工程质量 | **663 条测试通过**（另 9 条按 `slow`/`integration` marker 默认排除） | 2026-11-19 实测，76.95s |

> ⚠️ **不要再用旧的 `Recall@5 0.7347` 当主指标**。那是「标准答案与检索文档余弦相似度 ≥0.70 即算命中」的**历史代理口径**，只作历史对照，复现须加 `--legacy-similarity`。两套数字**不可直接比较**，口径见 11.4。

### 1.3 三条回答路径（理解系统的关键）

用户问一句话，系统可能走三条完全不同的路径。**看不清这三条，就会误判系统行为**（例如「为什么这个问题没有检索条数」）。

| 路径 | 触发条件 | 是否经过 LLM | 是否有检索证据 | 典型问题 |
|---|---|---|---|---|
| **工具直答** | 命中订单号/快递单号 → `sql`；命中售后结构化分流 → `policy` | 否（结构化直出） | 否 | 「我的订单到哪了」「退款多久到账」 |
| **RAG 检索生成** | 其余业务问题 → `retrieve` → `generate` | 是 | 是，带来源 | 「保质期多久」「礼盒里有什么」 |
| **转人工 / 待审批** | 情绪 extreme / 愤怒+高敏意图 / 明确要求办理退款 / 忠实度不达标 | 部分 | 视路径 | 「我要退款」「再不处理我就起诉」 |

> 这条区分来自 `src/graph/workflow.py` 的 `route_decision()`：售后类问题**优先**走 `policy` 结构化分流，未命中才回落到 RAG。因此售后问题「检索到 0 条」是正常现象，不是故障。

### 1.4 五分钟启动（零依赖演示）

```bash
git clone https://github.com/robben617/gift-rag-customer-service.git
cd gift-rag-customer-service
python scripts/demo_offline.py
```

不下载模型、不填 Key、不起 Docker。装了 Gradio 会自动开 `http://127.0.0.1:7863`，否则进终端问答。

> ⚠️ 这条链路**只做离线 FAQ 关键词检索 + 原文直出**（60 条 FAQ，字符二元组 IDF 加权，纯标准库），**不经过 LLM 生成、claims 核验与护栏**。它的输出**不代表系统真实回答质量**，只用于「先看见界面长什么样」。完整链路见第 10 章。

## 2. 业务背景与产品定义

### 2.1 业务链路（一个二维码怎么变成一次咨询）

| 环节 | 谁在动 | 发生了什么 |
|---|---|---|
| ① 选品采买 | 客户企业（运营/采购） | 按节假日档期采买礼赠品，以食品类为主 |
| ② 发放 | 客户企业 | 发给自有客户 / 员工，实物礼品随箱附卡片 |
| ③ **扫码** | 收礼用户 | 礼品外包装/卡片上的二维码是**唯一私域入口** |
| ④ 落地页 | 私域页面（H5/小程序） | 展示礼品详情、保质期、物流进度、售后政策 |
| ⑤ 咨询 | 收礼用户 → 客服 | 页面内嵌客服入口，**本系统在此介入** |

### 2.2 三个业务约束（所有技术选型的出发点）

**约束一：流量是脉冲，不是缓坡**

二维码在发货那一刻集中触达，用户几乎在同一周内涌入。行业公开经验值：节假日/大促峰值咨询量为日常的 **3–8 倍**（客服外包行业普遍按 3–5 倍配坐席，爆款品类可达 8–10 倍）。

> 📌 该区间为**行业经验值**，非本项目客户实测。客户侧真实日均/峰值量需由运营提供；做容量设计时按 3–8 倍预留。

**约束二：用户是被动收礼人，不是主动购物人**

他不熟悉品牌、没看过商品页、没有购物车与订单记录。因此问法极其口语化（「这玩意儿过期没」）、常常无主语且不带订单号（「能退吗」），必须靠会话记忆与追问补齐。

**约束三：答错代价严重不对称**

| 回答类型 | 答对收益 | 答错代价 |
|---|---|---|
| 商品规格 | 省一次人工 | 低，用户再问一次 |
| **食品保质期 / 过敏原 / 能否食用** | 省一次人工 | **食品安全事故、人身伤害** |
| **退款时效 / 赔偿标准** | 省一次人工 | **客诉、赔付、资损** |
| **价格与赠品承诺** | 省一次人工 | **「你们承诺过」，无法自证** |

> 结论：**不能用「整体准确率」衡量这个系统。** 「平均 95% 正确」在这里没有意义，因为剩下 5% 恰好落在最不能错的那几类上。这是「幻觉检测 + 高敏护栏 + 转人工」这一整条链路存在的唯一理由。

### 2.3 交付形态

**乙方交付**。开发方是软件交付团队，最终使用方是客户的私域礼赠业务团队。

对外表述统一为「**为客户交付的**私域礼赠智能客服系统」，不要写成「公司自己的业务」。

### 2.4 产品目标（按优先级，不可颠倒）

1. **高频咨询自助闭环** —— 能不转人工就解决
2. **转人工时体验不降级** —— 上下文无缝交接，用户不重述
3. **高风险回答不乱承诺** —— 先守红线，再谈效率

### 2.5 红线（不可突破）

- 食品安全、退款时效、价格承诺类问题 → **必须人工把关，或明确拒答**
- 任何回答**不得出现知识库无依据的具体数字**（几天、多少钱、百分之几）
- 检索不到时**必须说不知道**，不允许「根据常识推断」
- **系统不执行任何资金或订单写操作**：退款只能转人工，不能由模型代办

### 2.6 明确不做的事（范围外）

| 不做 | 原因 |
|---|---|
| 自动执行退款 / 改单 / 发券 | 资金与订单写操作必须人工，系统只读 |
| 替代人工客服团队 | 定位是「分流 + 兜底」，不是替代 |
| 商品推荐 / 营销触达 | 不属于客服场景 |
| 多租户 SaaS 化 | 当前为单客户交付，未做租户隔离 |
| 语音客服 / 电话外呼 | 当前仅文本（含 SSE 流式） |

## 3. 用户角色与权限模型

### 3.1 四个角色

| 账号 | 密码 | 角色 | 内容等级 | 能看什么 |
|---|---|---|---|---|
| `admin` | `admin123` | 管理员 | `vip` | 全部内容 + 管理面（上传/统计/评估/**审批**） |
| `vip` | `vip123` | VIP | `vip` | 全部内容，无管理权限 |
| `member` | `member123` | 会员 | `member` | public + member |
| `normal` | `normal123` | 普通 | `public` | 仅 public |

> 默认由 `ENABLE_DEMO_USERS=true` 开启（`.env.example`）。**生产必须置为 false**，否则明文弱口令直接暴露。

### 3.2 内容级权限隔离（本项目最容易被低估的设计）

权限模型不是「回答时过滤」，而是**检索时过滤**——不该看的内容根本不进入模型上下文。

```
public(0) < member(1) < vip(2)
可见性：用户等级(rank) >= 文档等级(rank)
Chroma filter: access_level <= {用户 rank}
```

三个关键实现细节：

1. **用整数 rank，不用字符串比较**。字典序下 `"member" < "public" < "vip"` 是错的，语义会错位。
2. **fail-safe 默认 public**。任何调用点漏传 `access_level`，默认取最低权限——宁可少给，绝不泄漏。
3. **缓存 key 必须含 access_level**。否则 VIP 命中过的缓存会被 public 用户读到，这是 RAG 系统最常见的数据泄漏路径。

单一定义源：`src/access.py`。全链路透传至六级降级 / 查询扩展 / 双路召回 / 自纠正 / 工作流兜底 / 审批恢复等路径。

### 3.3 v2.0 新增：审批面权限

| 动作 | 权限 | 隔离规则 |
|---|---|---|
| `GET /api/reviews` | 登录用户 | 默认只返回**自己**会话的任务；管理员可查全部 |
| `GET /api/reviews/{task_id}` | 所有者 或 管理员 | 所有者**只看到状态与已完成结果**；草稿、证据、管理员备注仅管理员可见 |
| `POST /api/reviews/{task_id}/decision` | **仅管理员** | 审批人用户名写入审计字段 |

> 会话与任务由已认证用户名绑定，**不能通过请求体指定另一个所有者**；权限被降低后，也不能用查询接口取回此前高权限任务的结果。

### 4.2 用户旅程（主流程）

```
扫码进私域页
   ↓
点客服入口，问「这玩意儿过期没」
   ↓
[classify_intent] 联合路由：intent=product_consult + rewritten_query（一次调用）
   ↓
[check_human] 情绪 calm、无敏感词 → 否
   ↓
[retrieve] L1 双路召回 → 命中 FAQ「保质期」
   ↓
[generate] 基于证据作答，附来源
   ↓
[evaluate_quality] claims 核验通过（faithfulness ≥0.7，高敏 ≥0.85）
   ↓
回复用户（本机实测 P50 7.83s，见 11.7）
```

异常分支 A：高风险草稿

```
用户：「退货运费谁出」
   ↓ [generate] 草稿忠实度 0.62
   ↓ [evaluate_quality] 未过 0.7 → 中断在 human_approval
   ↓ 写入审批表，返回 needs_human=true + review_task_id（用户看不到草稿）
管理员在管理台「回答审批」→ 批准 / 拒绝并重新检索
   ↓ 批准：原图从断点继续到结束，最终回答写入会话一次
   ↓ 拒绝：改写 → 重检索 → 重生成 → 再评；仍不过则生成新审批任务
```

异常分支 B：明确要求办理

```
用户：「我要退款，再不退我就起诉」
   ↓ [check_human] 情绪 extreme + 办理诉求 → needs_human，priority=high
   ↓ [human] 生成交接包（query/intent/emotion/entities/memory/attempted/reason）
   ↓ 客服在 7862 接手；用户在 7861 同窗口继续对话
```

### 5.4 检索降级 L0–L5

| 级别 | 策略 | 何时触发 |
|---|---|---|
| L0 | 复杂查询分解（「和/对比/区别」→ 子问题并行） | 检测到复合问法 |
| L1 | 双路召回稠密检索 + 合并去重 + Reranker | 默认路径 |
| L2 | LLM 改写查询 → 重检索（≤2 次） | L1 无结果或分数低 |
| L3 | Multi-Query + HyDE → 并行检索 | L2 仍不足 |
| L4 | 联网搜索（智谱 / Tavily） | 检索为空或降级≥4 |
| L5 | 诚实兜底（「根据已有信息无法确认，建议咨询人工客服」） | 全部失败 |

> 设计原则：**宁可说不知道，不许猜**。L5 是产品红线，不是技术失败。
> v2.0 补充：L2/L3 与最终兜底会**保留已召回的真实文档**，先做资料覆盖核验再决定，不再「一看分数不够就全丢」。

### 5.5 一次请求的完整链路（v2.0）

```text
JSON / SSE
  → chat_service.execute_chat（唯一共享入口）
  → PII 脱敏 → 会话锁（线程锁 + OS 文件锁）
  → 会话记忆读取（三层）
  → LangGraph 执行（13 节点）
  → 业务结果
  → 安全回复组装（未过核验的草稿在此被拦下）
  → 保存会话/记忆/监控（写失败不影响已生成的安全答复）
  → JSON 或 SSE 编码
```

**SSE 行为变化（v2.0，重要）**：`token` 事件现在表示**已核验的最终文本片段**，不再是模型生成中的原始 token。核验完成前会先发 `status` 与每 10 秒一次的 `: keep-alive`。代价是首字延迟变长，收益是**退款金额、承诺类文字不会先生成给用户看再被判错**。

## 6. 核心机制详解

### 6.1 「三个 faithfulness」不能混用（最容易出错的地方）

代码里有三套不同实现、不同量纲的数，**互相不可比较**：

| 名称 | 数值 | 实现 | 含义 |
|---|---|---|---|
| 历史评测脚本的 `faithfulness` | **0.657** | `metrics.py::calculate_faithfulness_fast` | 「标准答案 ↔ 检索文档」的 bge 余弦相似度，**仅检索模式的代理值** |
| 生成忠实度（G-Eval） | **暂无数字** | 需 `--legacy-similarity --with-generation --use-llm-eval` | LLM 对**实际生成的回答**逐条核验；**尚未留完整跑分** |
| 运行时护栏阈值 | 0.7 / 0.8 / **0.85** | `workflow.py:525`、`promise_guard.py` | `(supported + 0.5×partial) / 总claims`，作用于生成阶段 |

另有一个**看似 1.0 的第四种分**：支付政策原文答复的 `faithfulness=1.0` 来自**原文一致性校验**（回复逐字来自检索到的 FAQ），不是语义忠实度，**更不能拿来当整体质量指标**。

> 对外只能说：「检索侧代理值 0.657；生成侧忠实度还没跑完整 LLM 裁判，不给数字。」把 0.657 说成「生成忠实度 66%」是错的。

### 6.2 claims 级幻觉检测为什么重要

常见做法是让 LLM 自评一个 0–1 的「忠实度总分」。问题有两个：

1. **模型自偏**：倾向于给自己的输出打高分。
2. **均值掩盖**：10 句话里编了 1 句，总分可能还是 0.9，问题被平滑掉。

本项目改为：拆成 claims → 逐条判定 supported / partial / unsupported → 聚合。好处是**能定位到具体哪一句在编**，自纠正时也能针对性补信息。

### 6.3 高敏护栏的触发逻辑（注意：不是「一律」）

```
if 命中高敏（价格/退款/政策承诺） and faithfulness < 0.85:
    → 转人工核验
else:
    → 正常输出
```

同时，**明确要求办理的退款**走更硬的规则：`human_in_loop.py` 的 `refund_request` 场景直接判 `needs_human`，不依赖忠实度。

> 口径提醒：对外不要说「资金类一律人工把关」。准确表述是「**明确要求办理退款/退货的请求直接转人工；退款规则类咨询可自助解释；价格与政策承诺在忠实度低于 0.85 时转人工核验**」。

### 6.4 转人工与「待审批」是两条不同的路（v2.0 关键区分）

| | 直接转人工（工单） | 待审批（草稿复核） |
|---|---|---|
| 触发 | 情绪/意图/关键词命中 | 草稿未过质量评估，或需人工核验的高敏回答 |
| 用户看到 | 交接提示 + 客服接手 | 「已转人工核验」提示，**看不到草稿** |
| 落地 | `hitl_requests` 表 | `workflow_reviews` 表 + checkpoint 快照 |
| 处理者动作 | 客服直接对话 | 管理员「批准并发送」/「拒绝并重新检索」 |
| 恢复方式 | 人工会话 | **原图从断点继续执行** |

**转人工的判定来源（5 条）**

| 来源 | 规则 | 优先级 |
|---|---|---|
| 情绪 extreme | 辱骂/威胁/法律升级 | high |
| 情绪 angry + 高敏意图 | return_refund / complaint / order_query | high |
| 场景关键词 | `refund_request` / `complaint` / `sensitive_topic` / `high_value_order` | high / high / high / medium |
| 回答质量 | 评估未通过（含证据/回答覆盖失败） | low |
| 意图置信度 | `confidence < 0.4`（仅当调用方显式传入） | low |

**交接包内容**：`query + intent + emotion + entities + memory + attempted_actions + reason`。这是「用户不重述」的技术保证。

### 6.5 三层记忆

| 层 | 机制 | 解决什么 |
|---|---|---|
| 短期窗口 | 最近 6 轮原文 | 保证最近上下文精确 |
| 滚动摘要 | 窗口外对话 LLM 压缩（实体感知，600 token 预算） | 长对话不爆上下文 |
| 实体台账 | 正则抽取券/订单/金额，逐轮更新 | 「上次那个券」能解析到具体值 |

配套**指代消解护栏**：即使意图被分类为 `chitchat`，只要句子里含指代词（「那个」「它」「上次」），也强制走 RAG。

### 6.6 证据核验：先看资料有没有，再看回答全不全（v2.0 核心）

这是「有答案却转人工」从 10/18 修到 18/18 的关键。两道闸门：

| 闸门 | 组件 | 检查什么 | 不通过时 |
|---|---|---|---|
| **资料覆盖** | `AnswerabilityVerifier` | 资料是否覆盖当前问题；必须返回真实 `doc_id` + **逐字** `source_quote` | 拒绝恢复候选 → 转人工 |
| **回答覆盖** | 生成后复核 | 候选回答是否真的回答了问题；`answer_quote` 必须在回答中真实存在 | 触发自纠正或转人工 |

六个必须知道的实现约束：

1. **字段类型、未知文档、伪造片段、缺少支持一律拒绝**。模型说「有」不算，逐字片段必须能在原文里找到。
2. **HyDE 只是查询扩展，不能当事实证据**。
3. **核验失败按 `unavailable` 处理并转人工**，不能把服务故障算成「正确拒答」。
4. **谨慎限定 ≠ 整题无答案**。「未问的其他型号不保证」不应被判为答非所问；但明确型号、具体数值、安全保证、实际状态不能用通用说明补齐。
5. **输入哈希绑定**（问题 + 文档 ID + 实际可见前 800 字片段），同一输入可复用结论，问题或资料一变必须重验。
6. **达到循环上限也不能强制放行不合格答案**。

### 6.7 售后分流：咨询 / 办理 / 进度（v2.0 重写）

| 用户问法 | 处理方式 |
|---|---|
| 退款一般多久到账、帮我查退款政策 | 解释规则、起算条件与适用范围 |
| 怎么申请退款 | 说明操作流程，明确**没有代为提交申请** |
| 帮我退款、我要申请退货 | **转人工核对**，不执行资金变更 |
| 退款还没到账、查退款进度 | 转人工核对真实支付记录，不用「通常 1–3 天」代替实际状态 |
| 退款 | 先问：咨询规则 / 办理申请 / 查询进度 |
| 这盒礼品能退吗 | 先补齐品类、签收时间、退货原因、拆封情况 |

**政策数据结构**（`data/policies/returns.json`，v1，演示规则）：

`policy_id` / `version` / `effective_from` / `effective_to` / `notice` / `return_days` / `quality_days` / `refund_workdays_min` / `refund_workdays_max` / `excluded_categories` / `sealed_categories`

**返回状态** `policy_status`：`informational` / `clarify` / `conditional` / `not_applicable` / `manual_review`。

五个边界（容易被误讲）：

1. 条件齐全也只返回 `conditional`——**处于通用申请窗口，不代表退货获批**。
2. 生鲜、定制、贴身衣物、已拆封部分品类**不能套用**普通无理由条件。
3. 日期按**上海时区自然日差**计算；窗口边界测试覆盖第 7/8 天与质量问题第 15/16 天。
4. **不使用 mock 兜底**：数据库不可用、签收时间缺失或异常 → 转人工；不拿下单时间冒充签收时间。
5. 用户自述的品类/原因只作**待核实条件**，不采信 LLM 抽取结果，也不允许客户端伪造 `policy_context`。

### 6.8 支付政策原文答复（v2.0）

货到付款这类「规则明确但生成爱加戏」的问题，走一条**不调用生成模型**的分支：

```
意图路由 → 人工预判 → 带权限过滤的召回
   → 命中一份 faq_json，其问题与完整回答与核准 FAQ 完全匹配
   → 逐字引用 + 附引用编号（retrieval chunk ID / 序号）
```

三个约束：① 原问与补全问法都必须是**单一支付方式咨询**，追问订单状态/运费到付/其他问题则不触发；② 检索到另一份提及该支付方式的资料、或 FAQ 残缺改版 → 回落普通 RAG；③ 目前**只启用货到付款**一条核准规则，扩展需审核完整原文。

> 效果：固定集两轮货到付款的模型调用从 5 次/9 次降到 1 次/2 次；整组从 102 次、52,572 Token 降到 **91 次、46,735 Token**。

### 6.9 持久化审批与图续接（v2.0）

| 项 | 实现 |
|---|---|
| 暂停点 | `human_approval` 前中断，快照写 SQLite checkpointer |
| 任务状态 | `pending` / `processing` / `resolved` / `superseded` |
| 写入顺序 | **先写审批表 → 再改 checkpoint → 再恢复图** |
| 幂等 | 同一任务重复提交同一决定返回已保存结果，不重复生成、不重复入库；改成另一决定返回 **409** |
| 投递 | 结果先落库再做会话投递，用唯一 `event_id` 去重；中断可由重复审批/所有者查询/下次聊天补投 |
| 并发 | 同会话聊天与审批共用线程锁 + **操作系统文件锁**（同机多进程互斥，崩溃自动释放） |
| 旧任务保护 | checkpoint 内记录任务标识与已消费决定，防止故障重试把旧决定作用到新草稿 |

**别过度承诺**：这里保证的是「审批决定与最终投递幂等」，**不保证外部推理调用恰好一次**——故障发生在推理中，该节点可能重跑。文件锁只适用于**单机/本地部署**，未声称跨主机协调。

### 6.10 请求级追踪与用量（v2.0）

| 字段 | 含义 |
|---|---|
| `total_ms` | 共享服务入口到最终响应对象，含会话锁等待与记忆更新；不含落库与 HTTP 传输 |
| `stages` | 会话等待/各图节点/覆盖核验/生成/忠实度/改写/记忆读写；**嵌套阶段不能相加** |
| `llm_calls` | 逻辑调用数（含熔断器直接拒绝） |
| `llm_attempts` / `llm_retries` | 底层尝试数 / 首次之后的额外尝试 |
| `usage` | 供应商实际返回的非负整数 Token 之和，**不用字符数补算** |
| `usage_missing_attempts` / `usage_complete` | 用量缺失计数 / 是否完整 |
| `estimated_cost_cny` | 按仓库费率表估算；用量缺失或未知模型时为 `null` |

> 口径：**估算不等于账单**，未考虑供应商缓存折扣；Token 缺失时不能按 0 计。

同轮修复了一个真缺陷：原实现对 400/401/403/404 这类**不可重试错误仍然循环重试三次**，现在首次失败即停止（429/5xx/超时保留退避）。

### 6.11 发布门禁：用对话结果说话（v2.0）

`scripts/rag_release_gate.py` 跑两套**真实 HTTP** 对话，不是单元测试：

| 检查 | 要求 |
|---|---|
| 固定回归集（12 段 / 18 轮） | **18/18** 通过 |
| 新题集（15 段 / 17 轮） | **≥16/17**（90% 向上取整） |
| 两组风险与无证据题 | 风险漏拦 **0** |
| 两组证据题 | 每道题的证据组**至少命中一条**组内来源 |
| 执行与用量 | 逐轮完整，响应/追踪/Token 对得上；缺用量即失败 |
| 固定集 Token | 基线 51,834，+10% 余量 → **≤57,018** |

退出码：`0` 通过 / `1` 未通过 / `2` 用法错误。`--check-only` 只重算已有报告（无模型调用），但**源码指纹与当前代码不一致时报告自动失效**。

### 6.12 成本与稳定性

| 机制 | 数值 | 作用 |
|---|---|---|
| LLM 调用预算 | 8 次/请求 | 防自纠正叠加导致延迟与成本爆炸 |
| 自纠正轮次 | 3 轮上限 | 有界自主 |
| 熔断器 | 三态，LLM/Embedding 独立阈值 | 下游故障快速失败 |
| 缓存 | Query TTL 3600s / Embedding / LLM 响应 | 降本；Redis 不可达降级内存 |
| 重试 | 统一在 `LLMClient`；不可重试错误不重试 | 避免无意义调用 |

响应字段（v2.0 新增标 ★）：

| 字段 | 说明 |
|---|---|
| `query` / `intent` / `confidence` / `target` | 原问、意图、置信度、路由目标（rag/sql/human/policy/direct） |

| `emotion` | calm / dissatisfied / angry / extreme |
| `handoff_payload` | 转人工交接包 |
| ★ `trace_id` | 关联 `monitoring.db` 的 `query_id`，明细不对外返回 |

**审批**

```bash
# 列表（管理员可看全部，普通用户只看自己的）

  "http://127.0.0.1:8000/api/reviews?status=pending"

# 决定
curl -X POST http://127.0.0.1:8000/api/reviews/<task_id>/decision \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -d '{"decision":"approve","note":"核验完成"}'
```

**SSE 事件顺序**

| 事件 | 数据 |
|---|---|
| `status` | 处理与核验状态 |
| 心跳注释 | 等待期间每 10 秒一次，不是 JSON 事件 |
| `sources` | 最多三个去重后的证据文件名 |
| `emotion` | 与普通接口相同的情绪字段 |
| `handoff` | 需要人工时出现（reason / priority / payload） |
| `token` | **已核验**最终回复的文本片段 |
| `result` | 完整 `ChatResponse`，与普通接口业务字段相同 |
| `done` | `[DONE]`，正常结束时恰好一次 |

### 7.3 错误语义

| 状态码 | 含义 | 常见原因 |
|---|---|---|
| 401 | 未提供/无效凭据 | 没带 `Authorization`，或 token 过期 |
| 403 | 权限不足 | 非 admin 调管理面接口或提交审批 |
| 404 | 任务不存在或不可见 | 任务 ID 错误，或不属于当前用户 |
| 409 | 决定冲突 / 快照过期 | 已批准又改判，或旧草稿被新草稿取代 |
| 422 | 参数校验失败 | `query` 为空或超 1000 字符；`decision` 非 approve/reject |
| 503 | 依赖不可用 | 向量库/模型未就绪；审批服务暂时失败（可重试同一操作） |

| 7861 打开是空白/组件错乱 | 同进程 launch 多个 Gradio Blocks | 一个 UI 一个进程 |
| 聊天页恒显示「系统暂时繁忙」 | `API_BASE_URL` 没设，连了 `rag-api:8000` | `.env` 设 `http://127.0.0.1:8000` |
| `test_review_lifecycle` 整组报错 | 漏装 `langgraph-checkpoint-sqlite` | `pip install -r requirements.txt` |
| 审批通过后用户没收到 | 投递中断（服务重启/连接断） | 重复审批同一决定、或所有者查询、或下次聊天自动补投 |
| 审批返回 409 | 已批准又改判，或草稿已被新任务取代 | 用新任务 ID；不要对已 resolved 任务改判 |
| `/docs` 页面空白 | Swagger 静态资源走 CDN，被无代理环境挡住 | 需能访问 CDN 的网络/代理 |
| 端口被占 | 上一次进程未退 | `netstat -ano \| findstr :8000` → `taskkill /PID xxx /F` |
| 控制台中文乱码 | Windows 终端编码 | 设 `PYTHONIOENCODING=utf-8` |
| 检索结果为空 | 知识库空 / 阈值过高 / 权限不足 | 先 `ingest_faq.py`；再降阈值；最后确认账号等级 |

| 图片解析报 `Model does not exist` | SiliconFlow 模型名与账号权限不符 | `python scripts/debug_sf_models.py` |
| 想清空知识库重建 | — | 删 `data/chroma` → 重启 API → 重新入库 |

### 11.3 基线指标（固定 FAQ ID 基线，34 道可评分题）

| 配置 | Hit@5 | Recall@5 | MRR@5 | NDCG@5 | 查询平均耗时 |

| Dense + 重排（复跑） | 1.000000 | 0.990196 | 1.000000 | 0.990738 | 1405.021 ms |

> 出处：`docs/baselines/2026-11-16-dense.json`、`...-rerank.json`、`...-rerank_repeat.json`。
> 两次重排运行的逐题 Top-5 ID 与所有质量指标完全一致，说明该基线可复现。

**必须同时说的三条限制**：

1. 语料只有 60 条、题目偏易，**Hit@5=1.0 不代表线上准确率**。

2. **access_level fail-safe 默认 public**：改动方向只能是「更严格」。
3. **高敏阈值 0.85**：调低等于放行乱承诺。
4. **草稿不得进用户会话**：未审批的回答不能写入 `messages` 或记忆，否则审批形同虚设。

## 15. 附录

### 15.1 术语表

| 术语 | 含义 |
|---|---|
| **Agentic RAG** | 检索不是一次性的，而是带评估、自纠正、多级降级的闭环 |
| **L0–L5** | 六级检索降级：分解 → 双路 → 改写 → 扩展 → 联网 → 兜底 |
| **claims 级核验** | 把回答拆成若干断言，逐条判断有无证据支持，再聚合 |
| **资料覆盖 / 回答覆盖** | 前者判断资料是否够答，后者判断回答是否真的答了。两关都过才算合格 |
| **HITL** | Human-in-the-Loop；v2.0 为 SQLite checkpoint 持久化中断 |
| **review_task_id** | 待审批任务标识；用户只拿 ID，不拿草稿 |
| **交接包 handoff_payload** | 转人工时打包的上下文 |
| **access_level** | 内容等级 public(0) < member(1) < vip(2) |
| **chunk_id** | 分块唯一标识，双路召回按它去重 |
| **faithfulness** | 忠实度；**本项目有四种口径，见 6.1** |
| **policy_status** | 售后分流结果：informational / clarify / conditional / not_applicable / manual_review |
| **release gate** | 发布门禁；对话级质量 + Token 预算 + 源码指纹 |
| **trace_id** | 请求追踪 ID，关联 `monitoring.db` |
