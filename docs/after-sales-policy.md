# 售后咨询、办理与政策适用条件

本轮将“提到退款就转人工”改为按诉求分流，并把原项目中的示例退货规则移入 `data/policies/returns.json`。该文件是演示商家规则，尚未由真实商家核准，不是法律说明或生产承诺。

## 分流行为

| 用户问法 | 处理方式 |
|---|---|
| 退款一般多久到账、帮我查一下退款政策 | 解释规则、起算条件和适用范围 |
| 怎么申请退款 | 说明操作流程，明确没有代为提交申请 |
| 帮我退款、我要申请退货 | 转人工核对；不执行退款或资金变更 |
| 退款还没到账、查退款进度 | 转人工核对真实支付记录，不用“通常 1～3 天”代替实际状态 |
| 退款 | 先问是咨询规则、办理申请还是查询进度 |
| 这盒礼品能退吗 | 先补齐品类、签收时间、退货原因、使用/拆封情况等缺失条件 |

显式售后问法由共享规则分流，不再依赖 LLM 改写来保留“咨询/办理”的差别。投诉、法律升级、高情绪与食用后不适等原有或高风险人工路径继续保留。
这是有覆盖边界的确定性规则，不声称理解所有口语、否定或复合句；未明确覆盖的表达仍可能澄清或进入原分类链路。

## 条件判断

- 规则包含版本、生效时间、普通商品无理由窗口、质量问题窗口、特殊品类和退款工作日范围；每次读取并校验配置，不使用缓存中的旧政策。
- 通用退款时间说明从“仓库验收合格”起算，不等于这笔订单已发起退款，也不承诺具体到账时刻。
- 对具体商品，缺信息时返回 `clarify` 和待补字段；条件齐全也只返回 `conditional`，说明处于通用申请窗口，不代表退货/退款获批。
- 生鲜、定制、贴身衣物及已拆封的部分品类不能套用普通商品无理由条件；生鲜质量问题、活动专属条款、政策过期或超出通用窗口交人工核验。
- 日期按上海时区的自然日期差计算；示例窗口边界测试覆盖第 7/8 天及质量问题第 15/16 天。没有足够证据时不猜签收时间，也不把模糊日期当成有效条件。

`policy_status` 可为 `informational`、`clarify`、`conditional`、`not_applicable`、`manual_review`。JSON/SSE 的最终结果新增 `policy_status`、`policy_missing_fields` 和 `policy_version`，原有字段与接口参数保持兼容。
用户界面仍以中文回复说明需要补充的内容，不要求用户填写内部字段名。

## 事实与权限边界

用户自述的品类、使用情况和原因只作为待核实条件。系统不采信 LLM 抽出的品类或自由改写作为已验证事实，也不开放 HTTP 参数供客户端指定可信 `policy_context`。
已提及订单号的具体条件判断调用 `lookup_policy_order`，保留登录用户的 `user_id` 与管理员权限校验；不存在或无权访问统一提示无法核验，不泄露他人订单。
此政策查询**不使用 mock 兜底**。数据库不可用、实际签收时间缺失或时间异常时交人工；不使用下单时间或预计送达时间冒充签收时间。
真实订单签收记录优先于用户自述日期，订单创建时间不在当前规则版本范围内时也不能套用新版本。

现有 orders 表没有商品品类、SKU 专属规则或活动条款，因此本轮不假装具备这些数据。要做正式适用性判断，仍需商家提供对应数据与核准规则。

## 多轮澄清

结构化条件存入用户会话的 LangGraph checkpoint，并在紧接的相关补充中继续使用。只解析用户本轮补充与已存的结构化字段，不从助手回复或滚动摘要制造订单事实。
更换订单会清除旧品类、日期等条件；切换商品或话题也不会继续套用旧条件。同一事项随后明确要求办理时，已收集条件会随交接包带给人工。
SQLite 重建图后仍能承接尚未补全的条件；这不代表所有会话记忆模块都已持久化。

## 验证

新增测试覆盖咨询/办理/真实进度、否定和混合问法、规则版本失效、窗口边界、特殊品类、缺失/矛盾条件、订单归属、禁止 mock、可信签收日期优先、多轮澄清和 SQLite 重建后的继续澄清。
接口测试运行真实 LangGraph 和临时 SQLite，明确售后路径禁止落入泛化 LLM/RAG；JSON 与 SSE 使用同一结果。外部订单查询使用受控替身，不修改真实业务数据库，也没有真实退款写操作。

```powershell
python -m pytest tests/api tests/graph tests/conversation tests/engineering tests/business tests/orders tests/evaluation tests/admin tests/routing -q
```
